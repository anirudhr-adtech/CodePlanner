# MA plan: 12_crc32_engine

## S1. Frame the block as a data-transparent Ethernet-FCS tap on the 32-bit MAC stream that stalls only on a pending result

**Goal:** Write the Overview. The block observes a 32-bit valid/ready byte stream and never alters its data, keep or last. It computes the reflected CRC-32 FCS at one word per clock and emits one 32-bit result per frame, with status bits, through a single registered result slot. It back-pressures the stream only while that slot is occupied and not being drained, per the Q1 answer. State the TX (append) and RX (compare / residue_ok) use cases.

**Feeds:** Overview · **Depends on:** none

**Spec evidence:**
- [P2] "we need a CRC block that can sit on the receive and transmit data paths"
- [P5] "shouldn't modify the data stream; it just watches it, so it can be used as a "tap"."
- [P5] "own valid/ready so the TX side can append it and the RX side can compare it."

**Decisions:**
- D1 Tap behaviour: purely passive snoop vs data-transparent tap that can stall: **Data-transparent tap. Data, keep and last are never modified. The block holds one registered result slot. If that slot is still pending when a new beat arrives, last or not, the block deasserts its ready and the stream stalls. Results are never dropped.** (decided)
  - options: Purely passive snoop that never affects tready (needs result buffering and a drop policy) / Data-transparent tap that never modifies data/keep/last but withholds ready while its single result slot is full and undrained
  - The user's Q1 answer: single registered result slot, s_ready deasserts while a result is pending, no FIFO, no drop. This still honours P5's requirement not to modify the data stream.

**Done when:**
- Overview names both use cases: TX appends crc_data, RX uses residue_ok or crc_data
- Overview states the data stream is never modified and is stalled only while an unconsumed result is pending
- Throughput (1 word/clk, no inter-frame bubbles when the consumer reads the result promptly) and the 312.5 MHz target are stated up front

## S2. Define stream ports, stall/ready coupling, and the CRC result channel with residue_ok and error bits

**Goal:** Write the Interface and Parameters sections. Decide how the block sits on the stream, given that it must now drive a ready. List the result channel: crc_valid, crc_ready, crc_data[31:0], residue_ok and a per-frame error bit. List any sticky error output. Decide what is fixed and what is parameterised.

**Feeds:** Interface, Parameters · **Depends on:** S1

**Spec evidence:**
- [P3] "The data path inside the MAC is 32 bits wide, using an AXI-Stream-like valid/ready handshake."
- [P3] "On the last word of a frame we get a 4-bit byte-enable telling"
- [P5] "give us the final 32-bit CRC with its"

**Decisions:**
- D12 Physical placement of the stall: in-line pass-through vs off-path snoop with a stall output: **In-line combinational pass-through with no data registers. The only gating is slot_free = !crc_valid || crc_ready, applied to both m_tvalid and s_tready, so upstream and downstream always agree on which beats were transferred.** (default, medium impact, medium confidence)
  - options: In-line combinational pass-through: s_axis in, m_axis out, data/keep/last wired straight through, m_tvalid = s_tvalid && slot_free, s_tready = m_tready && slot_free / Off-path snoop inputs plus a 'crc_stall'/ready output that the MAC must AND into its own handshake
  - Gating both valid and ready inside the block guarantees that the CRC sees exactly the beats the sink accepts. Integration cannot get the AND wrong, and data is still not modified or delayed.
- D2 Data width parameterisation: **Fixed 32-bit data and 4-bit keep. Write the XOR-matrix generation as a synthesizable function so the width can be widened later without changing the architecture.** (default, low impact, medium confidence)
  - options: Fixed 32-bit data / 4-bit keep / Parameterised DATA_W with matrices generated by functions
  - The spec only gives 32 bits. A generic width adds verification cost now for no stated need.

**Done when:**
- Port table lists every signal with direction, width and meaning, including the gated ready/valid and the result channel
- The result channel carries crc_data, residue_ok and the per-frame error bit in a single valid/ready handshake, with no overflow flag
- Parameters table lists localparams for polynomial, preset, final XOR and residue constant

## S3. Pin down the reflected CRC-32 bit/byte mapping and the result format

**Goal:** Specify how tdata bytes and bits feed the CRC register, given byte 0 in [7:0] and reflected input. Specify how the final register maps to the 32-bit output, so that "123456789" yields 0xCBF43926 and TX can drop the result directly onto the wire.

**Feeds:** Datapath, Overview · **Depends on:** S1

**Spec evidence:**
- [P4] "polynomial 0x04C11DB7, register preset to all ones,"
- [P4] "reflected in and out like the 802.3 spec, and the result inverted at the end."
- [P4] "should produce 0xCBF43926"
- [P3] "Byte 0 of a frame is in bits [7:0] of the first word, byte 1 in [15:8], and so on."

**Decisions:**
- D3 Result data format on the CRC output: **Output the standard inverted, reflected CRC value. crc_data[7:0] is the first FCS byte transmitted, which matches the stream's little-endian byte order.** (default, medium impact, high confidence)
  - options: Standard CRC value (0xCBF43926 convention); its LSB byte is the first FCS byte on the wire when placed in [7:0] / Byte-swapped or bit-reversed raw register
  - This matches the spec's check value and the stream's byte ordering, so TX can append the result as one word and RX can compare it word-for-word.

**Done when:**
- The doc gives an explicit equation or mapping from tdata bits to the reflected LFSR input
- The "123456789" → 0xCBF43926 check is worked through as a 9-byte frame split into 3 words (keep 1111, 1111, 0001)
- Byte order of the result relative to the wire is stated

## S4. Design the single-cycle 32-bit parallel CRC datapath with partial-word last beat and SOF preset

**Goal:** Write the Datapath section. Cover the CRC state register, the parallel next-state logic for 4/3/2/1 valid bytes, preset injection on the first word of a frame, the final inversion, the residue compare, and capture into the single result slot.

**Feeds:** Datapath, Block Diagram · **Depends on:** S3

**Spec evidence:**
- [P5] "We need to process a full word every clock with no bubbles between frames, because the MAC"
- [P3] "only see 0001, 0011, 0111 or 1111 there"
- [P3] "any length from 1 byte upward"

**Decisions:**
- D4 Partial last-word CRC computation: **Compute four parallel update matrices (1-4 bytes) from the current state in the same cycle and select one with the decoded tkeep on the last beat. Non-last beats always use the 32-bit matrix.** (default, medium impact, high confidence)
  - options: Four parallel update matrices (8/16/24/32-bit) from the same state, selected by tkeep / 32-bit update followed by a reverse-shift correction / Byte-serial over multiple cycles for the tail
  - Keeps one word per clock with no tail cycles. Each matrix is a shallow XOR tree that fits 312.5 MHz and ports to ASIC.
- D5 Back-to-back frame state handling: **An SOF flag is set at reset and after every tlast beat. On an SOF beat the update uses 0xFFFFFFFF as the current state, so a new frame can start the cycle right after the previous tlast.** (decided)
  - options: Mux the all-ones preset into the state input when the beat is a start-of-frame (no idle cycle) / Reset the state register in a separate cycle after tlast
  - The spec requires no bubbles between back-to-back frames.

**Done when:**
- The block diagram shows the pass-through wires, slot_free gating, state register, preset mux, four update matrices, keep-select mux, inverter, residue comparator and the single result register
- A 1-byte single-beat frame (SOF and tlast on the same beat, keep=0001) is handled
- The keep-to-matrix-select mapping is tabulated

## S6. Specify the single-slot result channel and the stall it imposes on the stream

**Goal:** Define the result-channel handshake and the stall rule from the Q1 answer. There is one registered slot and no FIFO or drop. While the slot holds an unconsumed result, every new beat waits, last or not. Show that with a prompt consumer (crc_ready high when the result appears) back-to-back frames see no bubbles. Note the optional register slice for consumers that need full decoupling.

**Feeds:** Control Logic, Interface, Corner Cases & Error Handling · **Depends on:** S2, S5

**Spec evidence:**
- [P5] "give us the final 32-bit CRC with its"
- [P5] "streams back-to-back frames."
- [P7] "but don't hang."

**Decisions:**
- D6 Result-channel buffering and backpressure policy: **Single registered result slot with slot_free = !crc_valid || crc_ready. When the slot is not free, the stream is stalled for every beat. Results are never dropped, so there is no overflow flag. An external register slice on the result channel is the documented option for full decoupling.** (decided)
  - options: Small FIFO plus sticky overflow flag; drop results on overflow / Single registered result slot; stall the stream while the result is pending / Assume the consumer is always ready
  - User answer to Q1.

**Done when:**
- The doc proves no bubble occurs for back-to-back frames, including consecutive 1-word frames, when crc_ready is high in the cycle crc_valid rises
- The doc describes stall behaviour when crc_ready is held low, and shows the stream resumes the cycle crc_ready returns
- The combinational crc_ready → s_tready/m_tvalid path is called out for integration and timing

## S7. Specify RX FCS handling via the residue_ok flag over data+FCS

**Goal:** Document that the CRC runs over every observed byte, including the received FCS on RX. residue_ok is set when that CRC equals the 802.3 good-frame residue, so no lookahead or delay line is needed. Explain the TX and RX usage.

**Feeds:** Datapath, Interface, Overview · **Depends on:** S3, S4

**Spec evidence:**
- [P5] "own valid/ready so the TX side can append it and the RX side can compare it."
- [P2] "compute the Ethernet FCS on the fly"

**Decisions:**
- D7 RX handling of in-stream FCS bytes: **Compute the CRC over every observed byte. Output a residue_ok status bit on the result channel that is true when the CRC over data+FCS equals the 802.3 good-frame residue (0x2144DF1C in the inverted-output convention, 0xDEBB20E3 on the raw register). RX may use residue_ok or compare against a separately extracted FCS.** (decided)
  - options: Compute over all observed bytes; also output a residue_ok flag / Mode input that excludes the last 4 bytes, using a one-word delay line / Assume RX strips the FCS before the tap
  - User answer to Q2.

**Done when:**
- The residue constant is stated in the same bit convention as crc_data, and it is noted whether the compare uses the pre- or post-inversion value
- The doc explains that TX ignores residue_ok and that RX ignores crc_data if it relies on residue_ok

## S8. Close timing at 312.5 MHz and fix result latency

**Goal:** Write the Timing & Pipeline section. Identify the critical paths: the CRC loop (state → matrix → keep mux → state) and the combinational crc_ready → slot_free → s_tready/m_tvalid path. Estimate XOR depth on UltraScale+ 6-LUTs and on ASIC. State that the result appears 1 cycle after the tlast beat.

**Feeds:** Timing & Pipeline · **Depends on:** S4, S6

**Spec evidence:**
- [P6] "Target clock is 312.5 MHz on an UltraScale+ part."
- [P6] "We'd like to reuse the block on ASIC later."

**Decisions:**
- D8 Result latency and pipelining: **Keep the state loop single-cycle and register the inverted result and status into the result slot, so crc_valid asserts 1 cycle after the tlast beat. Data-side pre-registering is an allowed fallback if timing fails. It would add latency and move the stall point, and the doc must describe that.** (default, medium impact, medium confidence)
  - options: Unpipelined state loop; result registered and valid 1 cycle after the tlast beat / Pipelined data pre-processing, adding latency / Combinational result in the same cycle as tlast
  - The 32-bit CRC loop is a few LUT levels and should meet 3.2 ns. A registered result gives clean timing to the consumer and matches the single registered slot.
- D9 Implementation portability: **Pure generic synthesizable RTL with no vendor primitives.** (default, low impact, high confidence)
  - options: Pure generic RTL (no vendor primitives) / Use UltraScale+ specific primitives/attributes
  - Required for ASIC reuse (P6). XOR trees infer well on both targets.

**Done when:**
- A cycle-by-cycle timing diagram shows back-to-back frames including a 1-word frame, the result appearing one cycle after each tlast, and a stall case with crc_ready held low
- Both critical paths are identified with estimated logic levels and a fallback (pre-registered data terms, external result register slice)

## S10. Enumerate malformed-input and stall corner cases with a non-hanging error policy

**Goal:** Write the Corner Cases section. Cover illegal last-beat keep (0000, non-packed patterns), keep≠1111 on non-last beats, 1-byte frames, back-to-back single-word frames, mid-frame stalls from either side, and crc_ready held low indefinitely. Give the reporting mechanism for each and show the block cannot deadlock.

**Feeds:** Corner Cases & Error Handling · **Depends on:** S5, S6, S7

**Spec evidence:**
- [P7] "If something is malformed (for example a weird byte-enable), flag it somehow, but don't hang."
- [P3] "only see 0001, 0011, 0111 or 1111 there"

**Decisions:**
- D11 Malformed byte-enable policy: **Still end the frame on tlast and emit a result with a per-frame error bit set. Use a deterministic fallback byte count, defined by the MA writer. Also raise a sticky error output for the MAC status logic.** (default, medium impact, medium confidence)
  - options: Flag a per-frame error bit on the result channel; compute with a defined fallback byte count; still end the frame on tlast / Drop the frame's result entirely / Assert a separate sticky error output only
  - Satisfies 'flag it' and 'don't hang'. It keeps exactly one result per frame, which the no-drop single-slot policy relies on.

**Done when:**
- A table lists each anomaly with detection logic, CRC value produced, flags set and recovery
- The doc argues that no input pattern deadlocks the block: a stall persists only while crc_ready is low, and a malformed frame cannot corrupt the next frame's preset
- The doc states that the only stall source is a pending result owned by the consumer
